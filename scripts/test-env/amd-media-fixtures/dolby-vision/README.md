# Synthetic Dolby Vision acceptance fixtures

This generator creates four seconds of original procedural 320 x 180, 24 fps,
10-bit HEVC media. Every access unit receives a real, CRC-protected Dolby Vision
RPU generated by the pinned open-source `dolby_vision` library. The positive
profile 8.1 fixture deliberately changes the luma reshaping curve, so merely
copying a Dolby Vision configuration tag cannot pass the pixel-difference gate.
There are no downloaded film frames, third-party audio, fonts, or sample clips.

The first remote generation built the Rust generator and encoded the base, but
failed before MP4 muxing because FFmpeg 9 discarded output-only raw-input color
properties. This revision corrects the input/frame declarations and adds encoded
signal checks; remote generation `dv-fixtures02` subsequently passed on CT 104.
Product results and remaining gates belong to the
[phase 1 execution record](../../../../docs/development/amd-media-phase1-20260919.md).
Generation and acceptance must run on an authorized Linux worker. The presence
of these scripts is not evidence that the Dolby Vision acceptance gate has passed.

## Generation

Copy this directory to the designated worker, then run this command there,
substituting its actual private toolchain paths:

```sh
python3 scripts/test-env/amd-media-fixtures/dolby-vision/generate.py \
  --output /var/tmp/goby-dovi-fixtures-20260919 \
  --ffmpeg /path/to/private/bin/ffmpeg \
  --ffprobe /path/to/private/bin/ffprobe
```

The output directory must not already exist. The source directory is not modified.
The script builds the small RPU generator inside the output directory, generates
the procedural PQ chart, encodes its base layer once, and injects one RPU after
each access unit. The base uses Main 10 with a 24-frame GOP and no B frames. It
uses `dovi_rpu=compression=none` while copying the bitstream
to MP4 so FFmpeg writes the matching profile 8.1 decoder configuration; it does
not use that configuration as a substitute for RPUs. `-strict unofficial` is
required by FFmpeg's MP4 muxer to retain the `dvvC` box.

The base chart is tagged as limited-range BT.2020 non-constant-luminance PQ. Its
pixel values were authored as PQ code values from the start. The grayscale
stripes have 10-bit Y values `64, 128, 256, 384, 448, 512, 640, 720`, neutral
Cb/Cr of `512`, a horizontal PQ ramp, and a moving neutral patch. It is not an
SDR chart relabeled as HDR.

The raw input and the frames entering libx265 explicitly carry this authored
signal. This matters with FFmpeg 9: encoder initialization copies color properties
from the first frame, while output filter negotiation forwards matrix/range but
not primaries/transfer. Output-only color options therefore do not reliably
declare a raw input's primaries/transfer. The generator supplies input properties
and `setparams` before encoding, then checks the encoded base and every injected
stream with FFprobe. A mismatch in Main 10, bit depth, range, matrix, primaries,
or transfer fails generation before muxing. These declarations describe the
original PQ samples and do not perform an SDR-to-HDR conversion.

Using GOP 24 avoids x265's automatic Main 10 Intra / Range Extensions profile
for `keyint=1`. The uncompressed RPU mode keeps full mapping data on every frame:
in FFmpeg 9's RPU writer, only the `limited` and `extended` compression modes may
set `use_prev_vdr_rpu`.

For the product's positive integration test, set
`GOBY_TEST_DOLBY_VISION_FILE` to `profile81-nonidentity.mp4`,
`GOBY_TEST_VAAPI_DEVICE` to the worker's render node, and
`GOBY_FFMPEG` / `GOBY_FFPROBE` to its private tools. Run
`TestDolbyVisionActualRPUChangesPixelsAndProducesSDRAndHDR10` through the parent's
remote stage acceptance command.

The luma polynomial is exactly `f(x) = 1/16 + 3*x/4` on normalized encoded
component values. The integer/fractional coefficient pairs have denominator
`2^23`: offset `524288 / 8388608`, slope `6291456 / 8388608`. Chroma mapping is
identity. The intended result remains neutral grayscale, with deliberately
raised very dark samples and reduced bright samples before display mapping.
This is an analytic signal-processing control, not an artistic Dolby Vision grade.
The SDR output should declare BT.709 and 8 bits; HDR10 output should declare
BT.2020, PQ, and 10 bits. Both must have the source DV metadata removed.

For the same encoded input and target range, enabling RPU application must
change decoded pixels relative to disabling it. The integration gate currently
requires mean absolute grayscale difference greater than 0.1. Codec and tone
mapping choices can affect the exact output values, so neither this threshold
nor a metadata tag alone establishes colorimetric accuracy. Inspect the neutral
chart and retain the actual per-target pixel-difference evidence.

For this exact procedural chart, `GOBY_TEST_DOLBY_VISION_CHART=1` adds decoded
RGB stripe checks: neutral channel balance, monotonic brightness, retained
dynamic range and raised black. HDR10 additionally checks the authored
bright-stripe reduction in the PQ domain. SDR also applies BT.2390 display
mapping. The no-RPU control disables Dolby Vision color/HDR interpretation as
well as reshaping; its final highlight is not a direct comparison of just the
authored polynomial. The production graph disables peak detection. These bounded
signal checks do not establish certification or a proprietary reference match.

Count raw RPU NALs or per-frame `AV_FRAME_DATA_DOVI_RPU_BUFFER` for coverage.
Counting `AV_FRAME_DATA_DOVI_METADATA` alone is insufficient: FFmpeg can retain
mapping/color state from a previous frame after a later RPU is missing.

## Profile 7 scope

The pinned library identifies profile 7 with
`vdr_rpu_profile=1`, `el_spatial_resampling_filter_flag=1`,
`disable_residual_flag=0`, and `vdr_bit_depth_minus8=4`. Real MEL therefore has
the residual-disable flag cleared. MEL is identified by all three NLQ components
having `nlq_offset=0`, `vdr_in_max_int=1`, `vdr_in_max=0`, and zero integer and
fractional dead-zone slope/threshold values. FEL cannot be safely classified
from the header flag alone.

The profile 7 RPU files exercise these real structures and retain the
nonidentity curves. The corresponding `bl-rpu-only.mp4` files have correct RPU
syntax and a deliberately incomplete container declaration: profile 7,
compatibility ID 6, RPU/BL/EL flags set, but no EL video. Their purpose is to
exercise a strict filter's zero-NLQ decision and nonzero-NLQ rejection. The helper
adds a `dvcC` box to the final `moov` without changing any media sample offsets.
These assets cannot establish complete profile 7 input conformance. Constructing a
complete profile 7 positive video still requires a matching enhancement-layer
bitstream, correct dual-layer multiplexing/configuration, and separate acceptance.
A profile 8 RPU with a profile 7 container tag is not that evidence. The FEL
metadata control does not implement or demonstrate enhancement-layer reconstruction.

## Complete synthetic single-track MEL fixture

`profile7_mel.py` prepares a separate positive candidate containing a real,
independently decodable enhancement-layer bitstream. The earlier
`profile7-mel-bl-rpu-only.mp4` remains an incomplete control; this script neither
overwrites it nor reclassifies it. Preparing the new script is not generation
or product acceptance evidence. Its successful remote run must retain the
checks below before the resulting file is used as a positive product input.

The input is an existing, successful `generate.py` output. Its manifest must bind
the original 320 x 180 base layer and all 96 Profile 7 MEL RPUs by SHA-256. The new
script authors 96 frames of 160 x 90 YUV 4:2:0 10-bit samples with code value 512
in all three components and encodes them as a genuine Main 10 HEVC stream. This
EL is a neutral residual carrier, not another presentation image. It uses the
same 24 fps clock, 24-frame GOP, one slice per picture, and no B frames as the BL.
The real RPU's three-component zero NLQ makes the EL samples contribute no
residual. The RPU still contains the nonidentity luma mapping used by the P8.1
control. `disable_residual_flag` remains false, as required by this P7 syntax.

The multiplexing implementation is the pinned official `dovi_tool` CLI, not a
placeholder NAL or an EL flag added to a single-layer file:

- [`src/dovi/muxer.rs`](https://github.com/quietvoid/dovi_tool/blob/614c816b6446dcd1dbaf433403d499a6026fbb5a/src/dovi/muxer.rs)
  defines `EL_NALU_PREFIX = [0x7e, 0x01]`. `ElHandler::process_nals` prefixes each
  actual EL NAL with those two bytes, retaining the inner HEVC header and payload.
  RPU NALs remain standalone UNSPEC62. The resulting access unit contains BL
  NALs, UNSPEC63-wrapped EL NALs, then its corresponding RPU.
- [`src/dovi/general_read_write.rs`](https://github.com/quietvoid/dovi_tool/blob/614c816b6446dcd1dbaf433403d499a6026fbb5a/src/dovi/general_read_write.rs)
  removes the two-byte wrapper when demuxing UNSPEC63 and sends the RPU to the EL
  output. This restores the real EL parameter sets and slices.
- [`tests/hevc/demux.rs`](https://github.com/quietvoid/dovi_tool/blob/614c816b6446dcd1dbaf433403d499a6026fbb5a/tests/hevc/demux.rs)
  documents the official muxed-file to independent BL/EL contract.
- [`dolby_vision/src/rpu/rpu_data_nlq.rs`](https://github.com/quietvoid/dovi_tool/blob/614c816b6446dcd1dbaf433403d499a6026fbb5a/dolby_vision/src/rpu/rpu_data_nlq.rs)
  supplies the exact `is_mel` predicate. The script checks every exported RPU
  against all seven three-component NLQ arrays, not just the residual flag.
- [FFmpeg's `dovi_isom.c`](https://github.com/FFmpeg/FFmpeg/blob/n9.0.1/libavformat/dovi_isom.c)
  supplies the decoder-configuration packing. After checking actual elementary
  BL/EL/RPU payloads, the script appends a P7 `dvcC` with level 1, compatibility
  ID 6, and all three presence flags. It uses a single `hev1` video track and a
  final `moov`, so adding the configuration does not change sample offsets.

In addition to the base generator's prerequisites, compiling this fixed CLI
requires **Rust 1.95.0 or newer**, as declared by its top-level `Cargo.toml`.
The small RPU generator's Rust 1.88 prerequisite does not apply to the CLI.
Use a private toolchain prefix on the authorized worker and preserve any existing
toolchains. `--dovi-source` must be a pristine checkout at the exact revision
above, including its official `Cargo.lock`. The script builds with `--locked`,
one Cargo job, and `--no-default-features --features internal-font`. The official
CLI also compiles its plot command and needs this internal font implementation
even when only mux/demux/export are used; no system font packages are required. It records
the source revision, lockfile, built executable hash, tool versions, commands,
and their output. It does not fetch an encoded video or any audiovisual sample.

Run only in a fresh, owned remote output scope. For example, with worker-specific
paths and its private Rust `bin` directory already on `PATH`:

```sh
python3 scripts/test-env/amd-media-fixtures/dolby-vision/profile7_mel.py \
  --fixtures /path/to/retained/dv-fixtures02 \
  --dovi-source /path/to/pristine/dovi_tool-614c816b \
  --output /path/to/new/profile7-fixture01 \
  --ffmpeg /path/to/private/bin/ffmpeg \
  --ffprobe /path/to/private/bin/ffprobe
```

The output must be outside both input directories and must not already exist.
Do not run it locally or silently resume a failed output directory. Preserve all
failed logs and use a newly admitted output scope after repairing the cause.

A successful run requires all of the following:

1. Official `export` parses all 96 input RPUs, including their CRCs; each must be
   P7 MEL with explicit current mapping, 10-bit BL/EL, 12-bit VDR, and zero NLQ in
   every component. No previous-frame RPU mapping is accepted.
2. The official mux output must match the exact BL bytes, wrapped real EL bytes,
   and corresponding RPU for every access unit. BL and EL must share the same
   random-access NAL-type sequence.
3. FFprobe must recover the truthful P7 configuration from the final MP4. Every
   MP4 sample must contain one BL slice, one wrapped EL slice, and exactly its
   original RPU, with PTS = DTS = frame index / 24 and duration 1 / 24.
4. The script extracts HEVC from that final MP4 and invokes official `demux`.
   The recovered EL plus RPU must match every original NAL byte. Every recovered
   BL slice must match its source, and all extracted RPUs must match their source
   bytes and pass the official parser again.
5. Both original layers and both recovered layers must independently decode to
   96 frames with FFmpeg's fatal decode-error policy. The retained `framemd5`
   records must show identical source/recovered pixels, the expected dimensions,
   and the same 0 through 95 frame timeline at 1/24 seconds for both layers.
